# 1.2.6 배포 조건 팝업 CTD 점검

## 범위와 결론

- 대상: 배포된 1.2.6, 커밋 `b7fa52dbb470b2d2e7ac58e52b68cecdacf1a3b1`.
- 제보: 기존 세이브에 설치했을 때 배포 성공, 새 게임에서는 조건 팝업을 여는 Distribute 버튼에서 CTD. 재설치/설정 삭제로 해결되지 않음.
- 제보 환경의 게임 버전, 발생 탭, 게임 메모리 및 충돌 로그는 확보하지 못했다.
- **실제 CTD 원인은 아직 확정하지 못했다.** 아래 재현은 엔진을 제외한 UI 검증이며, 게임 폼 접근이나 RaceMenu 호출의 안전성을 증명하지 않는다.
- 아래 초기 조사는 1.2.6 진단 기록이다. 이후 승인된 1.2.7 수정과 검증 결과는 마지막 절에 구분해 기록했다. MO2 교체와 배포는 이 작업에서 하지 않았다.

## 실제 호출 순서

`NativeMenu::PostDisplay` → UI 그리기 → `OpenDistributionEditorFromCatalog`:

1. 선택 항목 수 확인. 0이면 알림 후 종료.
2. `EnsureDistributionEditor`: 저장된 규칙의 복사본을 얻고, 첫 진입이면 `RefreshDistributionTargetOptions` 실행.
3. 새 규칙 생성 및 선택 항목 복사, 벡터에 추가하고 마지막 인덱스를 선택.
4. `RollbackSingleCatalogPreview`: 해당 탭의 미리보기 복구 작업을 예약.
5. 팝업 표시 플래그 설정, 체크박스 모드 종료.
6. 같은 UI 프레임 후반 `DrawDistributionPopup`에서 조건 창을 그림.

이 버튼은 `ApplyLoadedNPCs`나 규칙 JSON 저장을 호출하지 않는다. 이들은 팝업 안의 명시적 실행/저장 버튼 경로다. 다만 미리보기 복구 작업은 별도로 예약되므로 외형 작업이 전혀 없는 버튼은 아니다.

## 격리 재현 결과

- 현재 소스에서 추출한 `DrawDistributionPopup`가 1.2.6 커밋의 동일 함수와 줄바꿈을 제외하고 일치함을 확인.
- 프로젝트에 포함된 실제 ImGui 및 `PopupPlacementUI.h`로 Debug 실행파일 구성.
- 한국어/영어/중국어 × 4개 배포 탭 × 규칙 수 0/1/20 × 선택 인덱스 0/19/999 × 11개 scope = **1,188개 조합**, 각 4프레임(열기/표시/닫기) 통과.
- 게임 데이터 수집, 외형 복구, 저장, 게임 입력은 stub 처리. 조건 드롭다운을 펼치거나 사용자 버튼 클릭 전체를 재생한 테스트가 아니다.
- 테스트 소스/실행파일은 무시되는 `build/diagnostics/distribution-popup` 및 `build/windows/x64/debug/PopupHarness.exe`에만 생성.
- 따라서 단순 빈 규칙 벡터, 첫 규칙 표시, 선택 인덱스 초과가 이 팝업 함수에서 곧바로 충돌한다는 가설은 재현되지 않았다.

## 남은 조사 우선순위

1. **첫 진입 시 조건용 폼 수집.** `RefreshDistributionTargetOptions`가 UI 그리기 콜백에서 TESDataHandler의 팩션/종족/키워드/클래스 배열을 직접 순회하고, `GetFile`, `GetName`, `GetFormEditorID`를 호출한다. UI 생명주기 mutex는 게임 폼 배열을 보호하는 락이 아니다. 별도 게임 작업 큐/불변 스냅샷/세션 취소 경계가 없다는 사실은 확인했지만, 제보 환경에서 실제로 동시 변경이나 무효 폼 접근이 발생했다는 증거는 없다. 새 게임에서 다른 모드가 해당 배열을 변경한다고 단정할 수 없다.
2. **미리보기 종료 후 엔진 호출.** 바디는 BodyMorph 미리보기 키를 제거하고 실제 키가 있었다면 `ApplyBodyMorphs`를 호출한다. 스킨은 이전 스킨 또는 기본값으로 복구한다. 핸들·세션·3D 확인은 있으나 엔진 제외 UI 재현으로 이 경로를 판정할 수 없다. 프리셋 선택값이 없다는 이유만으로 null 역참조가 일어나는 코드는 확인되지 않았다.
3. **새 게임 UI 초기화 비대칭.** `kPreLoadGame`에는 `ui::OnLoadStart`가 있지만 `kNewGame` 분기에는 직접 호출되지 않는다. 규칙 편집기 초기화 역시 UI 로드 경로에 있다. 동일 프로세스에서 기존 게임 → 새 게임 전환 시 남은 UI 상태를 별도로 검증할 필요가 있다. 이것만으로 새 프로세스에서 시작한 새 게임의 CTD를 설명할 수는 없다.

위 후보를 수정했다고 해서 제보 원인이 해결됐다고 발표해서는 안 된다. 코드상 위험 경로 제거와 제보 환경의 인게임 재현 해결은 구분해야 한다.

## 추가 추적

- 실제 `FrameTaskQueue`로 제출/동일 채널 교체/액터 취소/세션 초기화/지연 콜백 조합 250,000단계 실행, 37,505개 콜백 처리: 예외·잔존 작업·유효한 구세션 lease 없이 통과. 게임 엔진 콜백 내부는 검증하지 않는다. 진단용 `QueueHarness.cpp`만 build 하위에 추가했다.
- 신규 규칙은 벡터에 추가한 **뒤** 마지막 인덱스를 선택한다. 바디/스킨/후타/오버레이 각 목록에는 배포 모드 전환 프레임의 목록 렌더를 건너뛰는 검사가 있어, 체크박스 행 수와 기본값 행 수가 섞여 즉시 인덱스가 틀어지는 경로는 확인되지 않았다.
- 조건 옵션 `DistributionTargetOption`이 보존하는 것은 소유 문자열과 정수 ID다. `RE::TESForm*`를 보관하지 않는다. 따라서 새 게임에 캐시가 남는다는 사실만으로 dangling form pointer CTD라고 설명할 수 없다. 이전 캐시의 의미적 유효성 문제와 메모리 수명 문제를 구분한다.
- 바디 미리보기 취소는 `CancelPreviewTracking`으로 세대를 바꾼 뒤, 핸들과 세션을 검사하는 게임 작업을 예약한다. `ClearPreviewNow`는 인터페이스·핸들·3D를 검사하고 실제 미리보기 키가 있었을 때만 `ApplyBodyMorphs`를 호출한다. 최초 적용값이 없다는 이유만으로 그 ID를 무조건 역참조하는 경로는 아니다.
- 스킨 취소는 이전 ID가 비었으면 기본값 복원, 있으면 이전 팩 적용으로 분기한다. NativeSkinBackend에서도 ActorBase/소유권/요청 세대 검사가 있다. 이것이 RaceMenu의 실제 재생성 과정까지 안전하다는 증명은 아니다.
- 오버레이는 팝업 진입의 `RollbackSingleCatalogPreview`에서 별도 복구 분기를 실행하지 않는다. 따라서 오버레이 탭에서도 동일하게 창이 뜨기 전 CTD가 난다면 바디 BodyMorph 취소만으로 전체 현상을 설명할 수 없다.
- 팝업 위치 저장 시 일반 파일 쓰기/JSON 예외는 `Settings::Save`에서 잡고 실패를 반환한다. 평범한 설정 파일 쓰기 실패가 무조건 전파되어 CTD가 된다는 가설도 코드상 뒷받침되지 않는다. 메모리 부족 등 모든 예외를 배제하는 뜻은 아니다.

우선순위는 첫 조건 데이터 수집과 실제 엔진 외형 복구 경로다. **현재까지 CTD를 재현하지 못했으며, 원인 확정이나 수정 완료로 해석하면 안 된다.** 단순히 수집을 게임 작업 큐로 옮기는 것만으로 임의의 손상 포인터까지 안전해지는 것도 아니다.

## 추가 조사: 마우스 입력과 메타데이터 접근

- 진단 하네스에 실제 ImGui 마우스 위치/누름/뗌 이벤트를 추가했다. 제품의 `DrawDistributionPopup` 본문은 유지하고 버튼 호출에 위치·활성화 계수만 계측했다. 3개 언어 × 4개 탭 × 3개 배율 × 20회 = **720회** 열기/추가/삭제/이동 버튼/닫기 흐름, **5,760회** 버튼 활성화를 통과했다. 마지막 규칙 삭제 뒤 빈 목록에서 다시 삭제하는 경우도 포함했다. 규칙 대상·선택 복사·엔진·저장 도우미는 여전히 stub이며, 이동 버튼은 실제 규칙 재정렬의 모든 경우를 검증한 것이 아니다.
- 최초 테스트 실패는 추가 직후 다음 프레임의 행 배치를 기다리지 않고 이전 좌표를 클릭한 하네스 문제였다. 배치가 안정된 뒤 좌표를 수집하도록 고친 후 통과했다. 이를 게임 CTD 또는 게임 마우스 버그 재현으로 해석하지 않는다.
- 기존 1,188개 표시 조합도 같은 실행파일에서 다시 통과했다. 실행파일은 `build/windows/x64/release/PopupHarness.exe`이며 제품 DLL은 빌드하지 않았다.
- `AddFormTargetOption`에는 null form/file, 빈 파일명, 0인 로컬 FormID, null/빈 이름과 EditorID 검사가 있다. `Lower`도 `unsigned char`를 거쳐 `tolower`에 전달한다. 따라서 단순히 이름 없는 폼이나 한글 이름이 있다는 이유로 CTD가 난다는 설명은 뒷받침되지 않는다. 손상된 비-null 포인터를 검증한다는 뜻은 아니다.
- 사용 중인 CommonLib 헤더/구현에서 이 경로의 키워드/클래스/팩션/종족 인덱스는 각각 0x04/0x0A/0x0B/0x0E이며, 로드된 파일 목록 접근은 SE/AE용 경로다. 이 검사에서 지원 런타임 간 잘못된 인덱스 선택은 발견하지 못했다. 실제 제보 런타임의 메모리 레이아웃을 검증한 결과는 아니다.
- `SavedRulesSnapshot`은 mutex 아래 값 복사를 반환한다. 배포 규칙 벡터를 게임 작업과 직접 공유해 UI 참조가 무효화되는 구조는 아니다.

**해석:** UI의 단순 표시/버튼/빈 규칙 문제에 대한 근거는 더 약해졌다. 남은 엔진 경로를 배제하지 못했다는 사실이 곧 그 경로에서 충돌했다는 증거는 아니다. 특히 조건 폼 수집은 기존 세이브 첫 진입에서도 실행되므로, 이것만으로 새 게임에서만 발생한다는 차이를 설명할 수 없다. 원인을 가르려면 실제 실행에서 조건 수집 완료 전인지, 미리보기 복구 작업 실행 중인지 구분할 단계별 관찰이 필요하다. 현재 제품 코드와 MO2는 변경하지 않았다.

## 추가 조사: 최초 바디 미리보기 취소와 RaceMenu 평균 모드

구체적인 **조건부 수치 이상 경로**를 발견했다. 제보 CTD의 확정 원인은 아니다.

- [RaceMenu 공개 구현, 고정 커밋](https://github.com/expired6978/SKSE64Plugins/blob/9ebcb733e17be695f994cd2e9cc383043446bc02/skee64/BodyMorphInterface.cpp)의 `Impl_ClearBodyMorphKeys`는 키를 지우지만 빈 슬라이더 map은 남긴다. `Impl_GetBodyMorphs`의 평균 모드는 map이 비었는지 확인하지 않고 크기로 나눈다.
- 따라서 특정 슬라이더에 BCNG 미리보기 키만 있었고 이를 취소하면, `iBodyMorphMode=1`에서 `0/0 → NaN`이 된다. 같은 슬라이더에 다른 키가 남으면 이 조건은 성립하지 않는다. 다른 슬라이더에 저장 값이 있는 것만으로는 막지 못한다.
- BCNG `ClearPreviewNow`는 preview/legacyPreview 키를 지운 다음 실제 preview 키가 있었다면 `ApplyBodyMorphs`를 호출한다. 배포 조건 창 진입은 이 취소를 예약하므로 해당 조건부 경로에 도달할 수 있다. 새 게임 전용은 아니며, 기존 세이브의 처음 만지는 슬라이더에서도 가능하다.
- RaceMenu의 후속 메시 계산에서 `NaN != 0`은 참이고 좌표 계산에 유한하지 않은 값이 전달될 수 있다. 이것으로 CTD가 반드시 발생한다고 말할 수는 없다.
- [RaceMenu 설정의 공개 기본값](https://github.com/expired6978/SKSE64Plugins/blob/9ebcb733e17be695f994cd2e9cc383043446bc02/skee64/main.cpp)은 `iBodyMorphMode=0`이다. 그 기본 합산 경로에서는 이 빈 map 평균 문제가 발생하지 않는다. 제보자의 설정과 DLL 구현은 알 수 없다.
- 해당 map 삭제·계산을 모사한 진단 프로그램 `MorphCancellationHarness`에서 3개 모드 × 3개 baseline × 4개 preview 값, **36개 조합**으로 수치 조건을 재현했다. 실제 RaceMenu DLL/Skyrim/렌더러를 실행한 것이 아니며 CTD 재현도 아니다.
- 첫 단계 `NPC distribution` 버튼은 가까운 액터 선택/카메라 복구를 수행하고, 체크박스 선택 후 `Distribute`가 조건 창을 연다. 제보는 후자를 가리키는 것으로 읽히지만, 전자였다면 조건 폼 수집 가설은 적용되지 않는다.

수치 이상을 피하려고 무조건 모든 모프를 지우면 다른 모드의 값이 손실된다. 빈 항목에 영구 0 키를 넣는 것도 이후 평균 계산의 분모를 바꾸므로 무해한 수정이 아니다. 이번에는 제품 코드를 바꾸지 않았고, 이 후보를 원인 확정으로 격상하지 않는다.

## 추가 조사: 지연 작업의 세션 경계와 실제 배포물

- `FrameTasks::Continue`의 후속 작업은 actor/channel이 0이므로 `Pump`의 플레이어 RaceSexMenu 검사만 보면 누락처럼 보인다. 그러나 `ActorEvents`는 RaceSexMenu 열림 이벤트에서 `CancelActor(player)`를 호출한다. 이는 진행 중 lease도 취소하며, `Continue`의 등록 검사 및 큐의 `Take`에서 취소된 후속 작업을 거부한다. 이 보호를 무시하고 후속 작업이 캐릭터 생성 중 반드시 실행된다고 결론 내리면 안 된다.
- 실제 `FrameTaskQueue`를 사용하는 `LifecycleQueueHarness`에서 후속 콜백 등록 전/후 × 액터 취소/세션 초기화 **4개 순서**를 검사했다. 구 작업은 실행되지 않았고 새 작업은 실행됐다. 게임의 실제 이벤트 전달·이미 실행 중인 엔진 호출의 중단을 검증한 것은 아니다.
- 스킨 `ApplyNow`의 요청 세대 및 ActorBase ID 검사, 얼굴 rebuild gate도 확인했다. `QueueRebuild`와 얼굴 처리에는 별도 상태가 있으므로 바디 미리보기 취소와 동일 경로로 묶어 원인을 주장할 수 없다.
- 로컬 배포 ZIP 및 소스 ZIP의 SHA256은 `release/SHA256SUMS v1.2.6.txt`와 일치한다. 소스 ZIP의 UI/FrameTasks/ActorEvents/NativeSkinBackend/RaceMenuBodyMorph/Distribution 6개 소스는 릴리즈 커밋 `b7fa52d`와 줄바꿈 정규화 후 일치했다.
- 배포 ZIP에는 `BodyChangeNG.dll`이 하나 있으며 SHA256은 `5CD881B418FF4453F0553870D78504EC1D768FC9617B93ED4DFCA9DF26FA465E`이다. 이 결과는 로컬 패키지 검사일 뿐 제보자의 설치 파일이나 DLL의 소스 대응을 독립적으로 입증하지 않는다.

현 시점에서 정상 설정의 새 게임 CTD는 여전히 재현되지 않았다. 다음 유효한 실험은 동일 재현 환경에서 **조건 목록 수집을 생략한 진단 빌드**와 **팝업 진입 시 미리보기 복구 예약만 생략한 진단 빌드**를 각각 비교하는 것이다. 전자는 조건 선택 목록이 비고 후자는 미리보기가 창 진입 시 남으므로 배포용 수정이 아니다. 한쪽에서 충돌이 사라져도 타이밍 변화에 따른 효과일 수 있어 원인 확정에는 추가 확인이 필요하다. 아직 해당 진단 DLL을 만들거나 MO2에 교체하지 않았다.

## 인게임 테스트 불가 조건에서 확인한 UI 상태 초기화 누락

사용자는 인게임 테스트가 불가능하다고 밝혔다. 이후 조사는 소스와 엔진 독립 검사로 한정하며 위 비교 DLL의 인게임 시험을 완료 조건으로 요구하지 않는다.

### 확인된 별도 결함

- 체크박스 배포 모드에서 본체 UI를 닫으면 `OnClosed → DiscardDistributionDraft → ClearDistributionCatalogSelection`으로 후보 ID는 비운다. 그러나 `g_distributionSelectionMode`와 `g_distributionFemale`은 초기화하지 않는다.
- `OnOpened`는 플레이어와 바디 탭으로 돌아가지만 이 두 상태는 그대로다. 바디 체크박스 모드에서 닫았다면 다시 열 때도 선택 모드로 판정하며 이전 남성/여성 선택을 유지할 수 있다. 다른 탭의 선택 모드도 해당 탭으로 돌아가면 남아 있다.
- `OnLoadStart → ResetDistributionEditor`는 pool을 **body로 변경**하지만 선택 모드는 끄지 않는다. 이전 스킨/후타/오버레이 선택 모드가 바디 선택 모드로 해석될 수 있는 초기화 불일치다.
- 릴리즈 소스에서 플래그를 false로 만드는 명시적 대입은 배포 취소와 조건 팝업 진입뿐이다. 본체 열기/닫기/로드에는 없다.
- 릴리즈와 동일한 `ResetDistributionEditor`, `ClearDistributionCatalogSelection`, `DiscardDistributionDraft` 본문을 분리한 `DistributionResetHarness`로 4개 pool × 2개 성별 **8개 조합에서 상태 잔류를 재현**했다. 세 함수는 `b7fa52d` 원문과 줄바꿈 정규화 후 일치한다. 엔진 및 저장 규칙 조회는 대체했다.

이는 메모리 누수가 아닌 **UI 세션 상태의 잔류**다. 동일 프로세스의 닫기/다시 열기 또는 세이브 전환과 관련되며, 실행 직후 새 게임에서는 플래그가 false로 초기화되므로 제보 CTD의 원인이라고 할 수 없다. 잘못된 모드 자체가 CTD를 발생시킨 것도 재현하지 않았다.

수정한다면 본체 UI 세션 경계에서 선택 모드·성별·선택 후보·관련 표시 상태를 일관되게 초기화해야 한다. 기존 미리보기 복구는 먼저 수행해야 하며, 조건 팝업 내부의 규칙 추가에 필요한 후보 복사를 중간에 지워서는 안 된다. **현재는 진단만 수행했으므로 제품 코드에는 수정하지 않았다.**

### 참조 수명 추가 확인

스킨/후타 Snapshot은 mutex 아래 벡터를 값 복사하므로 해당 그리기 프레임의 항목 포인터는 원본 카탈로그 교체와 분리된다. 오버레이 표시 포인터도 UI 측 캐시가 보유한 항목을 가리킨다. 각 카탈로그는 배포 모드/액터 선택 변경 프레임에 기존 행 렌더를 중단한다. 이 검사에서 팝업 진입 때문에 해당 목록 포인터가 무효화되는 경로는 찾지 못했다. 게임 Actor/Form 포인터의 수명까지 검증했다는 의미는 아니다.

## 요청한 세 경계의 검증 결과

### 1. 새 게임 초기화 순서

릴리즈 `b7fa52d`의 콜백 본문을 직접 추출해 호출 순서를 대조했다.

- `PreLoadGame`: 큐 비활성화/epoch 변경 → rendered outfit 초기화 → **UI OnLoadStart** → 액터 작업/이벤트 초기화 → 스킨 초기화.
- 직렬화 `Revert`: 큐 비활성화/epoch 변경 → rendered outfit 초기화 → 액터 레지스트리 Revert(세션 번호 변경, 얼굴/애드온 초기화) → 틴트 초기화. **UI 초기화 호출 없음.**
- `NewGame/PostLoadGame`: 큐 활성화/epoch 변경 → rendered outfit/액터 작업/이벤트 → BodyMorph/오버레이/스킨/바디 분류 초기화 → 초기 배포 예약. **UI 초기화 호출 없음.**

따라서 기존 세이브 로드에는 UI 정리가 있지만, BCNG의 Revert → NewGame 경로 자체에는 동일한 정리가 없다. 백엔드 미리보기 추적의 초기화와 UI 편집/선택 상태의 초기화는 별개다. 앞서 실제 UI 초기화 헬퍼 8개 조합으로 재현한 선택 모드 잔류도 다시 확인했다. `Draw`의 epoch 검사 때문에 이전 UI가 무조건 계속 그려지는 것은 아니며, 다음 `OnOpened`는 pending preview를 비운다. 게임 자체의 메뉴 hide 이벤트 발생 여부는 시험하지 않았다. **코드의 UI 초기화 비대칭/누락은 확인했지만 이것이 CTD라는 증거는 없다.**

### 2. 작업 취소 직전/직후 경계

`CancellationBoundaryHarness`는 실제 `FrameTaskQueue`와 소유자의 mutex 사용 방식으로 두 스레드를 만들고 latch로 다음 순서를 강제했다. 액터 취소/세션 reset × 3개 경계 × 100회 = **600회**다.

| 취소 시점 | 결과 |
| --- | --- |
| `Take` 이전 | 200회 모두 실행 안 됨 |
| `Take` 이후, `ValidLease` 이전 | 200회 모두 실행 안 됨 |
| `ValidLease` 통과 이후, callback 호출 이전 | 200회 모두 callback 실행 |

마지막 결과는 큐의 취소 검사가 **실행 진입을 원자적으로 막는 장벽은 아니다**라는 의미다. 이전 검사 결과를 “취소 후 어떤 상황에서도 실행되지 않는다”로 일반화하면 안 된다. 실제 body 작업의 세션/세대 검사와 skin 작업의 요청 세대/ActorBase 검사는 추가 보호다. 그러나 검사 후 임의의 동시 취소까지 실행 중인 네이티브 호출을 중단시키는 것은 아니다. 이 테스트의 callback은 엔진을 호출하지 않았다. SKSE 게임 작업과 lifecycle 이벤트가 실제 게임에서 이처럼 서로 다른 스레드로 겹친다는 것은 확인하지 않았으므로 **200건의 게임 버그나 CTD 재현이 아니다.**

### 3. 조건 목록 수집 중 변경

릴리즈의 `AddUniqueTargetOption`, `LocalFormID`, `AddFormTargetOption`, `RefreshDistributionTargetOptions` 본문을 그대로 `CollectionBoundaryHarness`에 연결했다. 네 함수 모두 릴리즈 원문과 줄바꿈 정규화 후 일치함을 확인했다. 게임 자료형은 가짜 저장소로 대체했다.

- 안정된 데이터에서는 null/중복을 안전하게 처리하고, 수집 후 원본 이름이 바뀌어도 이미 복사한 옵션 문자열은 유지됐다.
- 팩션/종족/키워드/클래스 각각의 수집 중 배열 변경을 결정적으로 주입했다. **4/4에서 검사 iterator가 무효화를 탐지했다.** 실제 잘못된 메모리를 역참조하는 대신 예외로 검출했다. 실제 엔진의 `GetName`이 배열을 변경한다는 가정이나 주장은 하지 않는다.
- 시험용 epoch만 수집 도중 바꾸면 함수는 이를 확인하지 않고 끝까지 수집했다. null DataHandler는 안전하게 빈 결과로 처리했다.
- CommonLib의 `GetFormArray`는 배열 참조를 반환하며, `BSTArray`의 iterator는 원시 포인터다. 현재 수집 경로에는 배열 변경과 공유하는 동기화/안정된 읽기 구간/세션 재검사 경계가 없다. UI mutex만으로 다른 모드나 엔진의 변경을 막지는 못한다.

이 테스트는 **수집 중 배열이 안정적이어야 한다는 전제**를 확인한 것이며, 실제 Skyrim에서 해당 변경이 발생한다는 검증은 아니다. 단순히 Actor/Form 포인터 목록을 복사하거나 `try/catch`를 붙이는 것만으로 폼 수명을 보장할 수도 없다. 개선 시에는 엔진 데이터의 안전한 접근 시점에서 소유 문자열/ID 스냅샷을 구성하고, UI에는 완료된 값만 게시하며, 세션 변경 시 결과를 폐기하는 경계가 필요하다. 게임 작업 큐로 이동하는 것만으로 임의의 외부 스레드 변경까지 해결된다고 주장하면 안 된다.

**초기 진단 단계의 범위:** 세 항목의 소스/엔진 독립 검증은 수행했다. 초기화 누락은 별도 결함으로 확인했으며, 나머지 둘은 동시 실행 시 보호의 범위를 명확히 한 결과다. 이 단계에서는 제품 코드, DLL, MO2, 릴리즈 ZIP을 변경하지 않았다.

## 1.2.7 수정 및 회귀 검증 — 2026-09-18

사용자가 발견된 문제 수정과 1.2.7 전환을 승인한 뒤 다음을 적용했다.

1. `ResetDistributionSelectionSession`을 본체 열기·닫기·게임 세션 초기화에 연결했다. 선택 모드·성별·pool·후보·오버레이 갱신 플래그·목록 revision을 일관되게 정리한다. 정상 닫기에서는 미리보기 복원을 먼저 요청한다. **조건 팝업 진입에서는 이 초기화를 호출하지 않아** 규칙 추가용 후보와 색상 선택을 보존한다. 명시적 저장 동작과 JSON/co-save 형식은 변경하지 않았다.

3. 조건 목록 수집을 game task로 이동했다. 요청 한 번당 로컬 값 스냅샷을 완성하여 게시하고 UI는 공유된 읽기 전용 결과만 사용한다. 새 `SessionSnapshot`은 mutex 아래 세대/대기 상태를 확인하여 close/reset 뒤 결과, 이전 요청의 실패 통지, 중복 게시를 거부한다. 실패 상태에서는 프레임마다 다시 요청하지 않고 본체를 다시 열면 재시도한다. 로딩·실패 중에는 해당 메타데이터 드롭다운만 안내 문구를 보여준다. 전체 NPC/이름 조건과 저장된 규칙은 지우거나 막지 않는다.
4. 작업 실행 직전과 바디 미리보기 복원·바디 모프/네이티브 스킨 변경 경계에서 현재 lease와 pump epoch를 재확인한다. 이미 시작한 엔진 호출을 중단하거나 임의의 외부 모드 쓰기를 원자적으로 막는 장치라고 주장하지 않는다.
