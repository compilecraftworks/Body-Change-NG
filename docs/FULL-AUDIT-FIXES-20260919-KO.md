# 전체 기능 점검 후속 수정·추가 검증 — 2026-09-19

> 아래 G/H는 최초 실패 주입 당시 기록이다. 이후 제품 수정과 SE/AE 읽기 전용 엔진 검증은 [G/H 후속 결과](NATIVE-LIFETIME-FOLLOWUP-20260919-KO.md)를 기준으로 한다. 아래의 ‘해결 미완료·진단만·게임 실행 없음’은 그 초기 단계에 한정된다.

## 범위와 결론

- 기준: v1.2.7 작업 트리. 기존 모드 삭제 준비·TNG/SOS 복원 변경을 유지한 상태에서 추가 수정했다. 버전 및 지원 런타임 표는 변경하지 않았다.
- [수정 전 점검](FULL-AUDIT-20260919-KO.md)의 A–F는 제품 코드와 회귀 검사에 반영했다.
- G/H는 실제 제품 함수 일부를 가짜 VM·폼 할당자에 연결해 실패를 주입했다. **응답 누락 시 대기 정체와 실패한 복제물의 직접 회수 부재를 확인했으며, 두 항목을 해결 완료로 처리하지 않는다.**
- 게임 실행·실제 세이브 왕복·메모리 계측·MO2 교체·ZIP 생성·GitHub 게시를 하지 않았다. 자동 테스트 통과가 모든 환경의 누수·CTD·회귀 부재를 보증하지 않는다.

### 저장·목록 검사

- 액터 0 / 1 / 16,383 / 16,384 / 16,385 / 33,000개의 실제 EncodeV6/DecodeV6 왕복 검사 통과.
- 액터 600명에 각각 128개 오버레이 항목을 넣어 문자열 상한을 넘는 분할 저장·색상 복원 검사 통과.
- 기록 쓰기 실패 시 이후 기록을 계속 성공 처리하지 않는 검사 통과. 원래 로더가 복수 ASTR 레코드를 처리하므로 새 저장 버전을 도입하지 않았다.
- 같은 베이스 1 / 2 / 32 / 256명 초기화 정책 검사: 얼굴 복원은 모든 참조, 공유 몸 복원에 따른 갱신 순회는 한 번. 32명 합성 사례에서 갱신 콜백 요청은 1,024회에서 32회로 감소했다. 실제 엔진 재생성 횟수 측정은 아니다.
- 카탈로그 교체 중 이전 독자의 내용 불변, 독자 해제 후 이전 스냅샷 회수, 새 카탈로그 텍스처 수 검사 통과.
- 1,000행 목록의 일반/체크박스 모드, 기본값 행 유무, 화면 밖 키보드 포커스 행을 포함한 클리퍼 검사 통과.

합성 1,000팩 사례의 기존 스킨 목록 복사+경로 집계 중앙값은 약 17.7 ms, 공유 스냅샷의 캐시된 개수 순회는 약 0.0004 ms였다. 이는 메타데이터 작업만 비교한 수치다. 파일 읽기·GPU·렌더링·실제 UI 전체 시간이나 게임 FPS 개선 수치로 사용하지 않는다.

## G. 얼굴 비동기 응답 누락 추가 검증

### 방법

`FailurePathTests`는 빌드 시 제품 `FaceSkinOverrides.cpp`의 `Callback`과 `Batch::Call` 본문을 그대로 추출해 가짜 VM 및 게임 작업 큐와 연결한다. 테스트의 Finish는 실제 소유 세대 확인만 반영한 축소 구현이며 제품의 텍스처 쓰기·롤백 전체를 실행하지 않는다.

### 확인한 6개 조건

1. VM이 호출을 즉시 거부: 실패 종료, 배치 메모리 해제.
2. VM이 수락을 반환했지만 콜백을 버림: 배치 메모리는 해제되지만 액터 요청의 `running`은 남음. **메모리 해제와 작업 상태 정리가 서로 다른 문제임을 확인했다.**
3. 정상 응답: VM 콜백에서 직접 진행하지 않고 게임 작업 큐에서 후속 처리·종료.
4. 이전 세션의 늦은 응답: 새 세션 상태를 쓰거나 새 작업의 `running`을 해제하지 않음.
5. 이전 활성 세대의 늦은 응답: 후속 쓰기 없이 배치 참조 해제.
6. 응답이 오래 지연되다가 도착: 지연을 성공으로 오판하지 않고 실제 응답 뒤 종료.

### 판단

- 응답이 끝내 오지 않으면 다음 얼굴 작업과 삭제 준비가 대기할 수 있는 코드 경로는 재현했다. 실제 RaceMenu가 사용자 환경에서 콜백을 버렸다는 증거는 아니다.
- 정상 네이티브 얼굴 접근과 구분한다. VM 대체 경로, 이전 노드 정리, 언로드된 액터의 저장 오버라이드 복원 등이 대상이다.
- 현재 삭제 준비는 이런 상태를 성공으로 표시하지 않는다. 그러나 제한 시간 뒤 미완료 판정은 `running` 정체를 해결하지 못한다.
- 이번에는 임의 타임아웃이나 `running=false` 강제 변경을 넣지 않았다. 이미 수락된 이전 Papyrus 쓰기는 C++의 요청 세대 변경만으로 취소되지 않으므로, 늦은 쓰기와 새 적용의 충돌까지 다루어야 한다.
- 남은 작업: 응답 포기·미완료 상태 전환·재시도 정책과 변경 채널 복원을 함께 설계하고, 제품 Finish/롤백까지 포함한 실패 주입 및 실제 VM 지연 검증을 해야 한다.

## H. 스킨 복제 실패·재생성 시 수명 추가 검증

### 실패 주입

동일 테스트에서 제품 `DuplicateForm`과 `CloneTexture` 본문을 그대로 실행했다. 다음 11개 종료 경로를 검사했다.

- 복제 후 decal 데이터 할당 실패 1개.
- TXST 채널 위치 준비 실패 1개.
- 채널 0–7 쓰기 실패 8개.
- 정상 성공 1개.

각 실패에서 제품 helper는 실패 결과를 반환하지만 생성된 폼의 회수 함수를 호출하지 않는다. 가짜 폼 레지스트리에서는 생성물이 유지된다. 원본 DDS 경로와 decal 값은 변경되지 않았고, 성공한 복제의 decal은 원본과 독립이었다.

**가짜 레지스트리의 보존 개수는 Skyrim 메모리 누수량이 아니다.** 실제 CreateDuplicateForm의 등록·할당 수명, 부분 Copy 상태, 엔진의 회수 경로를 이 검사로 증명하지 못한다. ARMO/ARMA 그래프 전체 생성과 TNG의 외부 참조도 이 할당자 모델에는 없다.

### 재생성·세션 경로 확인

- `ApplyNow`의 원본 교체 경로는 먼저 `RestoreOwnedPointers`로 BCNG 소유 포인터 및 private TXST 경로를 복원하고, `instance = {}` 후 새 그래프를 만든다.
- ArmorGraph/TextureBinding에 보관된 폼은 raw pointer다. 이 대입은 C++ 벡터·문자열·스냅샷을 정리하지만 엔진 복제 폼 자체를 해제하지 않는다. BuildInstance가 몸 그래프 생성 뒤 far-skin 생성에 실패하는 경로에도 별도 복제 폼 회수는 없다.
- 일반 스킨팩 간 전환은 기존 그래프를 재사용한다. `ResetSessionState` 역시 그래프를 남기고 선택·소유 상태만 초기화해, 같은 원본의 저장 불러오기마다 복제하지 않는다. 따라서 매 클릭·매 로드가 전부 누수라는 결론은 맞지 않는다.
- 이전 그래프는 TNG의 캐시된 자식 Skin Armor가 private ARMA/TXST를 참조할 수 있다. 포인터 분리만 보고 해당 폼을 파괴하면 use-after-free가 될 수 있다.

### 판단

- 실패·원본 교체가 반복될 때 생성물이 누적될 위험과 BCNG의 직접 회수 부재를 확인했다. 실제 엔진 메모리 계측 없이 확정 누수량·회수 안전성을 주장하지 않는다.
- 이번에는 원본 폼, 이미 공개한 복제 폼, 과거 캐시 DDS를 강제 삭제하지 않았다.
- 남은 작업: 공개 전 실패 복제물과 외부에서 참조 가능한 이전 그래프를 나눠 추적하고, 지원 엔진의 생성/파괴 계약을 확인한 뒤 회수 또는 제한된 재사용 정책을 결정해야 한다. 정상 전환·원본 교체·실패 반복·저장 불러오기를 별도 계측해야 한다.
