# 얼굴 부착 경계 추가 조사 — 2026-09-11

이 문서는 읽기 전용 조사 단계의 기록이다. 이후 구현한 시험 어댑터는
[시험 DLL 및 검증 기록](FACE-ATTACHMENT-TRIAL-20260911-KO.md)을 참고한다.

## 첫 캡처 조건 — 메인 메뉴 이전

- 툴레드 `SkyrimSE.exe`, PID 17716, SE 1.5.97에서 코드 영역만 읽었다.
- 사용자는 실행 중이라고 알린 뒤 **아직 메인 메뉴에 도달하지 않았음**을
  정정했다. 그 시점에 추가 프로세스 읽기를 중단했다.
- 따라서 이번 자료를 메인 메뉴 초기화 완료 상태의 최종 후킹/호환성 검사로
  사용하면 안 된다. 메인 메뉴 도달을 확인한 뒤 연결 지점의 바이트를 재확인한다.
- `OpenProcess(0x410)` 조회·읽기만 사용. 힙/액터/세이브 데이터 읽기,
  게임 함수 호출, 프로세스 메모리 쓰기, 후킹, DLL 배포는 하지 않았다.
- 자료: `build/audits/face-attachment-boundary/`. 게임 코드 캡처는
  Git/공개 Release/소스 ZIP에 포함하지 않는다.

## 이번에 확인한 내용

### 1. 얼굴 등록표 삽입은 포인터 참조 보관이다

`0x363F20` 내부의 두 CALL (`0x364088`, `0x3640C5`)은 `0x36A880`으로 간다.
삽입 함수는 TESNPC 키와 전달된 얼굴 NiPointer의 참조를 보관하고, 같은 키가
있으면 참조 증가/기존 참조 해제로 값을 교체한다. 얼굴의 추가 deep-copy는 없다.

함수 본문은 호출자의 다섯 번째 인자에서 얼굴 NiPointer를 읽는다. 여섯 번째
스택 인자는 호출부에 준비되어 있지만 캡처한 삽입 함수에서는 소비하지 않는다.
이 관찰만으로 다른 런타임의 ABI나 전체 등록표 계약을 보장하지 않는다.

### 2. 제거된 얼굴은 즉시 부모에서 떼는 함수로 보내는 것이 아니다

`0x361AE0`에서 호출한 `0xC61CE0`은 lock과 상태/참조 수 조건을 확인한 후,
일부 경우 `0xC624C0`을 통해 별도 노드 컬렉션에 참조를 보관한다.
확인한 함수 본문에는 부모 노드의 DetachChild 호출이 없다.

**그러므로 이 함수를 얼굴을 부모에서 직접 제거하는 함수라고 부르면 안 된다.**
컬렉션의 최종 처리 루프와 NPC 얼굴 조회 결과의 전체 소비자는 아직 미확인이다.
등록표에 실제 붙인 얼굴 대신 원본을 넣는 우회가 안전하다는 결론도 아직 아니다.

### 3. BSFaceGenNiNode 복제는 animationData를 공유한다

`CreateClone(0x3D8480)`은 새 0x168-byte 얼굴 노드를 만들고,
`CloneMembers(0x3D8560)`을 호출한다. 이 함수는 원본 `+0x150`의
animationData 포인터를 참조 증가 후 복제본 `+0x150`에 그대로 저장한다.

이는 단순 Clone이 얼굴의 모든 가변 상태를 독립 복제한다는 가정을 반증한다.
다만 같은 액터의 표정 상태 공유가 엔진 의도일 수도 있으므로, 이 관찰 자체가
현재 다른 NPC로 표정이 전파된다는 증거는 아니다. 액터 연결 단계에서 해당 참조가
어떻게 설정되는지 확인한 뒤 보존/격리 정책을 결정해야 한다.

### 4. TextureSet 경로만 교체해서는 로드된 얼굴 Diffuse가 바뀌지 않을 수 있다

FaceGen 재질 `OnLoadTextureSet(0x12D2300)`은 기존 Diffuse가 유효하면
실제 로딩 분기를 생략한다. 하위 base loader `0x12CF480`도 같은 조건을 갖는다.
로딩 분기를 실행할 때는 TextureSet의 index 0을 재질의 Diffuse 참조로 읽는다.

반면 `BSLightingShaderProperty::SetupGeometry(0x12C5450)`은 내부 geometry
설정 함수를 호출한 뒤 true를 반환한다. 확인한 내부 `0x12C5540`은 geometry와
shader flag 설정을 다루며, 이 경로에서 TextureSet 로더를 호출하지 않는다.
**SetupGeometry의 true를 DDS 로딩 성공의 증거로 삼으면 안 된다.**

이것은 새 부착 전 어댑터의 로딩/검증 순서를 정하기 위한 결과다. 기존 다른
기능의 텍스처가 반드시 로드되지 않는다고 단정할 수는 없다. 나중의 렌더링 경로가
별도 로딩을 수행하는지는 이 조사 범위에 포함되지 않았다.

### 5. FaceGen ClearTextures는 tint도 해제한다

`0x12D2420`은 base Diffuse/Normal 등 해제 후 `+0xA0` tintTexture,
`+0xA8` detailTexture, `+0xB0` subsurfaceTexture도 비우고 참조를 해제한다.
따라서 선택 DDS를 읽히려고 이를 호출하면 원래 얼굴 tint까지 사라질 수 있다.
새 어댑터는 원래 tint의 소유권과 유지/복원 순서를 따로 검증해야 한다.

## 검사 및 변경 범위

- 9개 직접 CALL 목적지와 8개 주요 필드/분기 명령을 캡처 원시 바이트로 재검산.
- 조사 도구의 `--attachment-boundary`에 이번에 확인한 직접 하위 함수 6개 추가.
- 플러그인 런타임 소스·설치 DLL·세이브는 이번 단계에서 변경하지 않았다.
- 새 얼굴 어댑터는 여전히 미구현이며, 이 결과를 인게임 적용 성공으로 보고하지 않는다.

## 메인 메뉴 도달 후 재확인

사용자가 메인 메뉴 도달을 알린 뒤 같은 PID 17716에서 다시 읽었다. 아래 내용은
앞선 미초기화 상태 자료와 구분된 `build/audits/face-attachment-main-menu/`에
저장했다. 모든 주소는 **SE 1.5.97 EXE의 RVA**다. AE에 재사용하지 않는다.

- `userReportedStage=main-menu`, 프로세스 접근 권한은 동일하게 `0x410`이다.
- EXE SHA256:
  `693e5a51ea2680119a68620bcf5080e81745549872b5d06bbd3f51131b67abab`.
- 최종 캡처 63개 코드 범위 중 기존 50개는 첫 캡처와 바이트 단위로 동일하다.
- 정확한 세 목적지 `0x363F20`, `0x364120`, `0x3641A0`의 직접 CALL 후보를
  실행 코드 영역 22,234,220바이트에서 검색했다. 전체 영역은 임시 읽기만 하고
  저장하지 않았으며, 예외 테이블로 범위를 확인한 후보 함수만 자료에 포함했다.
- E8 바이트 검색은 명령 경계 확인을 대체하지 않는다. 발견한 5개 후보는
  디스어셈블리에서 실제 명령 경계를 확인하고 상대 목적지도 재계산했다.

### 핵심 정정: TESNPC 등록표에는 실제 붙인 얼굴이 필요하다

`BipedAnim`의 `0x1CBC40`은 액터를 찾고 TESNPC를 얻어
`0x1CBCA0 → 0x3641A0`에서 얼굴 등록표를 조회한다. 반환된 얼굴을
`0x1CBCB0 → 0x1CBD10`으로 넘긴다.

`0x1CBD10`은 그 얼굴의 자식 지오메트리를 순회하며 dismember partition을
찾고, 장비 슬롯 번호와 비교한 뒤 `0x1CBE2A → 0x1CDD40`을 호출한다.
고정 Address Library의 SE ID 15576과 CommonLib 선언으로 확인한 후자는
`BSDismemberSkinInstance::UpdateDismemberPartion(slot, enable)`이다.
호출 직전 `R8=0`이고, leaf 함수 `0x1CDD77`에서 해당 partition의 표시 상태에
false를 기록한다. 즉 **등록표에서 꺼낸 얼굴은 장비 슬롯에 따라 숨길 실제
얼굴 지오메트리**다.

월드에는 복제 얼굴을 붙이면서 이 등록표에는 원본을 넣으면, 엔진이 화면과
다른 얼굴의 partition을 갱신하게 된다. 따라서 두 등록처를 구분한다.

| 엔진 저장 위치 | 유지할 값과 정책 |
| --- | --- |
| 공용 리소스 Model DB | 원래 로더 결과를 유지. BCNG 선택 DDS로 수정한 얼굴을 넣지 않음 |
| TESNPC 현재 얼굴 등록표 | 실제 액터에 붙인 얼굴. 원래 부착 함수의 삽입·조회·제거 흐름을 유지 |

**이전의 “복제 얼굴은 두 등록처 모두에 넣지 않는다”는 조건은 폐기한다.**
등록표 삽입 인자를 원본으로 바꾸거나 BCNG의 별도 얼굴 등록표를 만드는
후킹은 구현하지 않는다. 원래 로더와 Model DB 등록이 끝난 뒤, 부착 직전에
전용 인스턴스를 준비하여 원래 부착 함수에 넘기는 방향으로 정리한다.

이 결과가 동일 ActorBase를 공유하는 여러 액터의 독립 스킨 선택까지 증명하는
것은 아니다. 기존 shared-ActorBase 제한 정책은 변경하지 않았다.

### 부착 진입 경로와 남겨야 할 엔진 동작

직접 CALL 네 곳이 `0x363F20`으로 연결되는 것을 확인했다.

| 호출 명령 RVA | 포함 함수 시작 RVA | 확인한 동작 |
| --- | --- | --- |
| `0x14A033` | `0x149FE0` | 보유한 얼굴 NiPointer를 액터에 부착한 뒤 액터 handle을 얼굴에 연결 |
| `0x31A551` | `0x319E80` | 기존 얼굴 분리·등록 초기화·GetHeadModel 뒤 부착하는 분기 |
| `0x3652A7` | `0x364FF0` | 앞서 확인한 얼굴 준비 경로의 부착 |
| `0x65100E` | `0x650DF0` | AIProcess 3D 재구축 경로의 부착 |

세 대상 중 `0x364120`의 직접 CALL 후보는 없었다. 간접 호출·인라인 코드·
외부 DLL 경로까지 없다는 의미는 아니다. 또한 메인 메뉴에서 코드를 읽은
것이지, 플레이어/NPC를 로드해 이 경로를 실제 실행 추적한 결과는 아니다.

원래 부착 함수가 호출하는 `BSFaceGenNiNode::FixSkinInstances`의 진입부에는
이미 외부 JMP가 설치되어 있다. 후속 외부 코드 전체는 이번 범위에서 확인하지
않았다. 새 어댑터는 원래 부착/가상 호출을 보존해야 하며 기존 후킹을 덮어쓰거나
그 호출을 생략해서는 안 된다.

Character의 실제 `GetFaceGenAnimationData(0x693980)`도 현재 얼굴의
`+0x150`을 반환한다. 앞서 확인한 CloneMembers의 animationData 참조 공유를
완전한 독립 복제로 오해하지 말아야 한다. 액터 연결과 표정 수명은 보존 대상이다.

### 이번 단계의 결과와 구현 전 남은 확인

- 주요 직접 CALL 9개와 역할/필드 명령 3개를 원시 바이트로 재검산했다.
- 공용 모델 캐시와 현재 얼굴 등록표의 역할을 구분했고, 잘못된 삽입 우회
  설계를 제외했다. 이것이 이번 추가 조사의 실질적인 변경이다.
- 재질/TextureSet 독립 복제 후 이전 Diffuse의 유효 참조 때문에 로더가
  생략되지 않도록 해야 한다. FaceGen tint 보존과 실제 DDS 로드 결과 확인은
  새 어댑터 구현 시 필요한 별도 검증이다. SetupGeometry 반환만 검사하지 않는다.
- 등록표 제거 후 별도 컬렉션의 최종 처리 루프까지 증명한 것은 아니다.
  엔진의 참조/정리 흐름을 우회하거나 BCNG가 대신 해제하지 않는다.
- 이번 단계에서는 조사 도구와 기록만 수정했다. 게임 함수 호출·메모리 쓰기·
  런타임 소스 수정·시험 DLL 배포·세이브 변경은 하지 않았다.
- 새 얼굴 어댑터는 아직 미구현이다. 인게임 해결, NPC 간 격리, 세이브/로드,
  다른 SE/AE 런타임 호환이 완료됐다고 보고하지 않는다.
